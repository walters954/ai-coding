Retry counter: stop at three calls, fail fast on permanent errors

Scope: one function, fetchWithRetry, in an invented file src/net/retry.js. Committed change only; no staged, unstaged, or untracked files are involved. All code on this page is made up for teaching.

1. The problem

fetchWithRetry should try a request at most maxAttempts = 3 times. Two bugs crept in:

  • Off by one. The counter starts at zero and the loop runs while attempt <= maxAttempts, so a request that keeps failing is sent four times instead of three.
  • Retries everything. Every error is retried, including permanent ones such as a rejected payload or a missing record. Those can never succeed, so retrying them only adds delay and load.

The fix counts each call as it happens, stops after the third call, and lets permanent errors fail on the first call.

2. Before and after

Removed or replacedAdded or replaced

What changed

  • The counter is now attempts and is incremented before each call, so it always equals the number of calls made.
  • The limit moved out of the while condition into a single retry decision inside catch.
  • A new isTransient(err) check means permanent errors are never retried.

The classifier is invented too:

function isTransient(err) {
  return err.code === 'TIMEOUT' || err.status === 503;
}

3. Walkthrough

  1. Start at zero. attempts begins at 0: no calls have been made yet.
  2. Count, then call. Each loop pass runs attempts++ for the call about to happen. During the first call the value is 1; during the third it is 3.
  3. Success returns at once. If send resolves, its result is returned and the loop ends.
  4. Decide in one place. On an error, canRetry is true only when the error is transient and fewer than maxAttempts calls have been made.
  5. Otherwise rethrow. A permanent error, or a transient error on the third call, reaches the caller unchanged.

The first call fails with a 400 “invalid payload” error. isTransient returns false, so canRetry is false and the error is thrown after exactly one call. Before the fix, the same request was sent four times.

4. Risks and limits

  • No delay between attempts. Retries fire back to back. During a real outage this adds load; backoff with jitter would be a separate change.
  • Classification decides everything. If isTransient labels a permanent error as transient, it is retried up to three times; if it misses a transient one, the call fails early.
  • Side effects may repeat. Retrying a request that is not safe to repeat, such as creating an order, can duplicate it.
  • At least one call is always made. With maxAttempts of 0 or less, send still runs once and any error is thrown. Validate the option if that matters.
  • Tests worth adding. Exactly three calls for repeated transient failures; exactly one call for a permanent error; success on the second call returns the value.
